# FutureTech Level 1 — Missions 1–3 Opening Sequence Audit

**Status:** APPROVED / FROZEN OPENING SEQUENCE  
**Missions:** 1 — Make It Happen · 2 — Make It Think · 3 — Build a Game  
**Scope:** consistency and progression audit before Mission 4

## Final decision

Missions 1–3 form a coherent opening sequence and are frozen together as the approved start of FutureTech Level 1.

Only two high-value inconsistencies required correction:

1. Missions 1–2 still used partner-role language even though student work is individual by default.
2. Missions 1–2 still used older PASS / NOT YET checkpoint wording instead of the course-standard MISSION COMPLETE / RETRY ONE SKILL / SUPPORT ROUTE language.

Those issues are corrected. No instructional redesign was required.

---

## 1. Student independence

**Final status: aligned.**

All three missions now establish individual ownership of code, testing, explanation and checkpoint performance.

Collaboration remains only where it adds instructional value:

- brief TRY 4 troubleshooting conversation;
- peer playtesting in Mission 3;
- temporary hardware sharing when controller supply is limited.

Driver/Navigator, role-switch and pair-based Ready-for-Check language is not part of the approved opening sequence.

---

## 2. Visual and instructional language

**Final status: consistent and strong.**

The approved common pattern is:

**short instruction → block-finder chips → mini code model when structurally needed → observable success cue → TRY 4**

Mission 1:
- models first event/output structures;
- models two event stacks and a simple sequence.

Mission 2:
- models SET vs CHANGE;
- models random → IF → repeat nesting.

Mission 3:
- uses four path-specific models only where new game structure or platform mapping requires them;
- does not reveal the Stage 4 finished solution.

Visual scaffolding is intentionally maintained because it supports beginner independence without replacing student decision-making.

---

## 3. Scaffolding progression

**Final status: appropriate decrease in support.**

### Mission 1
Highest scaffolding:
- hardware identification;
- explicit input/output teaching;
- basic event placement;
- highly guided first code.

### Mission 2
Moderate scaffolding:
- assumes Mission 1 workflow;
- introduces variables, randomness, IF and repeat;
- models more complex nesting but expects more independent construction.

### Mission 3
Integration scaffolding:
- assumes prior coding routines;
- visuals focus only on new movement/rule structures and hardware-path differences;
- Build It, playtesting, improvement and checkpoint require substantially more independent application.

The sequence moves from **copy/compare → guided combine → independent integration**.

---

## 4. Coding concept progression

**Final status: logical and cumulative.**

**Mission 1:** events + input/output + sequence  
↓  
**Mission 2:** variables + SET/CHANGE + randomness + IF + repeat loop  
↓  
**Mission 3:** repeated motion + controller input + IF rule + score/end state + integrated game system

Mission 3 meaningfully reuses Mission 1–2 skills rather than reteaching them.

---

## 5. Workload and pacing

**Final status: appropriate for the 90-minute mission model.**

Each mission follows the same pacing logic:

- early visible success;
- guided skill building;
- required Build It creation;
- optional Level It Up;
- rolling Ready-for-Check;
- short individual checkpoint;
- Passport + Reset.

Mission 3 is the most complex but reduces unnecessary prose and limits the required game to one moving object, one main action, one rule, one score system and one end condition.

No workload reduction is required.

---

## 6. Checkpoints

**Final status: consistent with increasing independence.**

All three now use the same outcome language:

- **MISSION COMPLETE**
- **RETRY ONE SKILL**
- **SUPPORT ROUTE**

Checkpoint progression:

### Mission 1
Demonstrate input/output → explain event → make a small change.

### Mission 2
Explain variable/IF/loop → make a logic-related change.

### Mission 3
Play/identify → explain an integrated system → independently modify and test a game feature.

The cognitive demand rises appropriately while the checkpoint format remains familiar.

---

## 7. Skill Passport progression

**Final status: cumulative without unnecessary duplication.**

### Mission 1
micro:bit execution, input, output, event, sequence, basic change/test.

### Mission 2
variable, value change, repeat loop, randomness, IF, explain/change/test.

### Mission 3
game object, repeated game motion, controller input, IF-based game rule, playtesting/improvement, independent explanation/change/test.

Each Passport records newly demonstrated mastery rather than restamping the entire previous mission.

---

## 8. Hardware setup and Reset

**Final status: consistent.**

Missions 1–2 establish:
- numbered micro:bit kit;
- tested USB cable;
- save/download routine;
- equipment care;
- kit/workspace reset.

Mission 3 extends the routine only as needed:
- assigned controller station;
- controller return;
- controller fault reporting.

Hardware complexity grows without changing the basic classroom routine.

---

## 9. Mobile and readability consistency

**Final status: passed existing rendered-preview standard.**

The established requirements remain:

- desktop;
- Chromebook/tablet;
- 390 px;
- 375 px;
- 320 px;
- no horizontal scrolling;
- code models stack vertically;
- nesting remains visible;
- instructional cards collapse cleanly;
- path identity remains readable in Mission 3.

No shared responsive-style correction is required.

---

## 10. Duplication audit

**Final status: acceptable and purposeful.**

Repeated elements are routines students should internalize:

- stage architecture;
- TRY 4;
- Build It / Level It Up / Checkpoint;
- Ready-for-Check;
- Passport;
- Reset.

Concept explanations are not unnecessarily duplicated:
- Mission 2 briefly reconnects to Mission 1 rather than reteaching it;
- Mission 3 assumes prior event/IF/loop understanding and only gives a compact reboot;
- visual models repeat known structures only when required to support a new arrangement or hardware environment.

No meaningful duplication needs removal.

---

## Frozen opening-sequence rule

Future Mission 4+ authoring should preserve the strengths established here:

- individual student ownership by default;
- collaboration only when instructionally useful;
- strong visuals and mini models;
- short explanations;
- block-finder chips for unfamiliar blocks;
- observable success indicators;
- visual scaffolding that decreases as mastery increases;
- Build It as the student-owned creation;
- individual checkpoints;
- cumulative Skill Passports;
- consistent Reset routines.

Do not reopen Missions 1–3 for stylistic redesign. Future changes should be limited to evidence-based usability, accessibility, hardware-support or factual-correction needs.

**Mission 4 remains unbuilt and outside this audit.**
